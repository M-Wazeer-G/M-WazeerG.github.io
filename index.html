VendorLink

A platform connecting event organisers with vendors through event listings, vendor applications, organiser decisions and post-approval payments.

Open live website ↗View GitHub repository ↗
01

Project Overview

Purpose, scope and recorded functionality.

1.1 Purpose and problem

I worked with my teammates on VendorLink after seeing how difficult it was for vendors to find markets, expos and festivals in one place. We wanted to connect vendors and organisers through a shared platform for event listings, applications and decisions.

1.2 Core workflow

  1. I create an event and add a banner as an organiser.
  2. I find an event and apply for a stall as a vendor.
  3. I accept or decline an application as an organiser.
  4. After approval, I continue to PayFast when a fee applies.
  5. I check the payment status after confirmation as an organiser.

1.3 Technology and links

  • Source repository: VendorLink on GitHub
  • Application URL: vendorlink-1vla.onrender.com
  • Technology: Java 17, Spring Boot, PostgreSQL/Supabase, HTML, CSS, JavaScript, JWT and PayFast.

User Stories and Tasks

Reconstructed from the reported workflow and development history.

US-01 · Create an event

Story: As an organiser, I want to create an event so vendors can discover it.

Acceptance criteria: Required details can be entered, valid information is saved, and validation errors are clear.

Tasks: Build event form; validate fields; save event; test valid and invalid submissions.

US-02 · Upload an event banner

Story: As an organiser, I want to upload a banner so the event listing is recognisable.

Acceptance criteria: An image can be selected and uploaded; successful upload is reflected in the event; errors are handled.

Tasks: Implement upload; connect storage or image URL handling; display image; test supported and invalid uploads.

US-03 · Browse event listings

Story: As a vendor, I want to browse events so I can find opportunities.

Acceptance criteria: Event information is readable and closed/full events are not presented as open application opportunities.

Tasks: Retrieve events; display cards/details; show availability; test empty and populated results.

US-04 · Apply to an event

Story: As a vendor, I want to apply to an open event so the organiser can consider me.

Acceptance criteria: Application is recorded for review; closed/full events reject applications; duplicate applications are prevented.

Tasks: Submit application; validate event status and capacity; prevent duplicates; expose application to organiser; test outcomes.

US-05 · Review an application

Story: As an organiser, I want to accept or decline applications so I can manage participation.

Acceptance criteria: The event owner can review applications; the status updates; unauthorised users cannot decide on another organiser's applications.

Tasks: Build review controls; check ownership; update status; handle capacity; test accept and decline paths.

US-06 · Pay after acceptance

Story: As an accepted vendor, I want to pay the stall fee so my registration can be completed.

Acceptance criteria: Payment is offered after approval when a fee is due; amount is correct; opening checkout alone does not mark an application paid.

Tasks: Connect approval to checkout; pass amount/reference; handle cancelled or failed checkout; test payment initiation.

US-07 · Confirm payment status

Story: As an organiser, I want to see whether a vendor has paid so event participation can be managed accurately.

Acceptance criteria: Confirmed successful payment updates the status; failed/cancelled payment is not shown as paid; organiser can view status.

Tasks: Handle payment confirmation; validate notifications; update stored status; display status; test success/failure.

US-08 · View application status

Story: As a vendor, I want to view my applications so I know whether they are pending, accepted or declined.

Acceptance criteria: Vendor sees their own applications and current status; status reflects the organiser's decision.

Tasks: Retrieve current user's applications; display statuses; verify access restrictions; test updates.

US-09 · Enforce account roles

Story: As a user, I want role-based access so restricted actions and information are protected.

Acceptance criteria: Protected actions require authentication; vendors cannot perform organiser-only actions; organisers cannot manage events they do not own.

Tasks: Review authentication/authorisation; test role restrictions; inspect error handling and secret exposure.

US-10 · Handle notifications and errors

Story: As a user, I want clear feedback when an application or payment changes or fails.

Acceptance criteria: Status is clear; relevant notifications appear where supported; errors do not appear as success.

Tasks: Review notifications; check messages; test transitions and failures; document gaps.

US-11 · Respect event capacity

Story: As an organiser, I want approvals to respect stall capacity so the event is not overbooked.

Acceptance criteria: Available capacity is checked; approval reserves capacity; a full event cannot exceed its limit; capacity release is handled correctly.

Tasks: Review capacity rules; test full events and repeated decisions; check cancellation behaviour.

US-12 · Recover from errors

Story: As a user, I want clear messages when an action fails so I know what to do next.

Acceptance criteria: Validation/server failures are not treated as success; messages are understandable; failures do not create incorrect application/payment state.

Tasks: Test validation, server/network failures and payment failures; log defects; retest fixes.

3.1 Evidence

I reconstructed these 12 stories and task breakdowns from the workflow I reported and the development history. The acceptance criteria describe expected behaviour; they are not test results. The screenshots in Project Evidence show selected application states, and the Agile Logbook links related code changes.

3.2 Reflection

Writing the stories helped me connect the screens I worked on to what organisers and vendors need to do. As someone who started building full-stack applications this year, I used to think mainly about getting a feature working in my part of the code. Breaking it into acceptance criteria and tasks helped me see the complete path through the interface, API, database and payment response. Next time I would discuss the criteria with the stakeholder before development and record real test outcomes against each one.

4.2 Reconstructed priority order

Priority Backlog item Reason for priority
High Create and publish an event with a banner This gives vendors an event to discover and apply to.
High Browse events and submit a vendor application This is the vendor's main path into the platform.
High Review applications and enforce capacity Organisers need to manage participation and avoid overbooking.
High Offer payment after approval and show confirmed status This completes the paid-stall workflow while keeping payment status accurate.
High Protect accounts and organiser-only actions Authentication and ownership checks protect event and application data.
Medium Improve notifications, error handling, cancellations and refund requests These help users recover from changes and exceptions in the core workflow.

4.3 Reflection

Rebuilding the feature history showed me why a backlog needs both an order and a reason for that order. Our repository records what changed, but it does not show which features we considered first or why. I placed the event-to-application path ahead of supporting improvements because it delivers the main user value; I placed payment after approval because it depends on the decision flow. In future work, I would agree priorities with the stakeholder, keep them visible, and revisit them when new information changes the value or risk.

5.3 Reflection

I called our work one-week sprints, but we did not formally track a sprint backlog. Looking back, the commit totals help me see bursts of activity, but they cannot tell me what we planned, what carried over, or how much effort a task took. I also struggled with Render: the code could work locally while deployments failed repeatedly. That was frustrating, and it showed me that deployment checks need to start early in a sprint. In the proposed sprint above, I would make the goal and acceptance criteria visible, review progress and blockers during the week, and record the outcome whether a task passes or fails.

7.2 Reflection

Using the commits helped me reconstruct what I worked on and when, especially my backend and integration contributions. It also exposed how much context is lost when I rely on Git history alone: the reasons behind decisions, verbal feedback, task ownership and actual test results are not consistently recorded there. The gaps between commits do not prove that no work happened, but they make the project harder to explain. As Scrum Master, I would keep a short log during each sprint with decisions, blockers, test outcomes and links to the work, rather than trying to rebuild it at the end.

08

Individual Reflection

At the start of VendorLink, I saw that vendors did not have one place to find markets, expos and festivals. I wanted to help build a platform that could connect vendors and organisers. I worked with my teammates on the event-to-payment workflow, and the project grew from static pages into an application with a backend and database. This helped me understand how a real problem can guide the features I build.

I chose backend work because I had more knowledge in that area, and we used WhatsApp to communicate. When I needed images changed on the event listings, I asked Will to handle the frontend task, but the change did not get completed at the time. I took it over and made the edits myself. The change was done, but I could have explained the problem and agreed on ownership more clearly. I learned that communicating across frontend and backend work matters as much as being able to make the change myself.

In September, I helped move the project from a static prototype to a separate Spring Boot backend and frontend. My task included backend, database and integration work. I connected the frontend to the backend through Axios and helped configure Supabase. The project then had a separate backend, a connected frontend and a hosted PostgreSQL database. Since I only started full-stack applications this year, this work helped me see that a feature depends on data moving correctly between the interface, API and database.

I struggled with deploying VendorLink to Render. The code could be working locally, but the deployments failed repeatedly, which was frustrating and sometimes made me question what I had done wrong. I kept working through integration problems with CORS, authentication and API routes, and I helped connect the event, application, profile and notification services. When the main frontend services were calling the backend API, I felt relieved that our work was finally coming together. The experience taught me that a feature is not finished just because it works on my computer. Next time, I would deploy earlier, leave more time to work through failed deployments, and check the hosted version throughout development.

Online payments were future work in the first README. My backend role later included work on PayFast and the stall-fee changes. The recorded flow waits for PayFast confirmation before changing an application to paid, and free events do not require payment. This made me think about payment states, cancellations and refunds as part of the feature, instead of treating checkout as a separate screen. I found the changes in the repository log, but no end-to-end test results were recorded.

Challenges and Lessons

What I observed in the project record and how I would approach it next time.

What I observed What I learned
Deployment and integration fixes clustered on 1 October, about six weeks after the repository was created. I would deploy one small working feature earlier so that hosting and integration issues appear sooner.
We kept frontend files in both the Frontend folder and the backend static folder. I would keep one frontend source and automate copying it during the build, so the copies cannot drift apart.
Some commits used a generic author name, and one large frontend update went directly to main. I would configure Git identity at setup and use a pull request for changes that need team review.
I found no dated sprint plans, reviews, retrospectives or task-board updates in the repository log. I would keep short records during the work so the reasons for decisions and the work between commits are easier to trace.
